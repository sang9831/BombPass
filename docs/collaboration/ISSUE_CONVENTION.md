# GitHub Issue 컨벤션

작업 추적에는 Jira 대신 GitHub Issues를 사용한다. 제목과 본문은 한국어로 작성하고, 한 이슈에는 완료 여부를 판단할 수 있는 한 가지 작업을 담는다.

## 작업 타입 (Type)

이슈, 브랜치, PR, 커밋에 공통으로 사용하는 표준 타입 접두어:

| 접두어 | 설명 | 예시 |
|---|---|---|
| `feat` | 새로운 기능 추가 | `[feat] 대기실 참가자 목록 표시` |
| `fix` | 버그 수정 | `[fix] 재접속 후 게임 상태 미갱신 오류 수정` |
| `docs` | 문서 추가 및 수정 | `[docs] README 프로젝트 소개 및 실행 가이드 개선` |
| `chore` | 빌드, 패키지 매니저, 설정, 저장소 잡무 | `[chore] GitHub 워크플로 CI 설정 추가` |
| `refactor` | 코드 리팩토링 (기능 변경 없는 개선) | `[refactor] Redis 세션 저장 로직 모듈화` |
| `test` | 테스트 코드 추가 또는 테스트 환경 개선 | `[test] 폭탄 소유권 이전 동시성 테스트 추가` |
| `style` | 코드 포맷팅, 스타일 수정 (로직 변경 없음) | `[style] ESLint / Prettier 적용` |

## 제목

`[타입] 작업 요약` 형식으로 작성한다.

- 기능: `[feat] 대기실 참가자 목록 표시`
- 버그: `[fix] 재접속 후 게임 상태 갱신 오류 수정`
- 문서: `[docs] API 명세서 갱신`
- 잡무: `[chore] 의존성 버전 업데이트`

## 본문

GitHub Issue 등록 시 제공되는 템플릿(`feat`, `fix`, `chore` 등) 중 알맞은 것을 선택한다. 본문에는 해당되는 항목을 채운다.

- 배경과 해결할 문제
- 기대하는 동작 또는 구체적인 작업 범위
- 완료 조건(체크리스트로 작성)
- 재현 절차와 실제/기대 결과(버그인 경우)
- 관련 문서, 화면, 로그 등 필요한 참고 정보

요구사항 문서에서 정책이 미확정이면 확정된 동작처럼 기술하지 말고, 미결정 사항으로 표시한다. 비밀값, 인증 정보, 사용자 개인정보는 이슈에 올리지 않는다.

## 연결 및 브랜치 규칙

- 기존 이슈가 작업과 일치하면 새 이슈를 중복 생성하지 말고 기존 이슈를 사용한다.
- 작업 브랜치는 반드시 **타입 접두어**와 **이슈 번호**를 포함하여 명명한다.
  - 형식: `<type>/<issue-number>-<short-description>`
  - 예시:
    - `feat/12-lobby-player-list`
    - `fix/23-reconnect-state`
    - `docs/2-readme-documentation`
    - `chore/1-repo-init`
- 이슈 번호나 저장소의 기준 브랜치를 임의로 추측하지 않는다.
